# CyberScan security tools 051-100

Owner: Agent 2. Date: 2026-11-11. Status: **implemented and tested; not approved in `registry.json`, not committed, not deployed.**

Fifty tools in five categories, each a single module that plugs into the existing `Tools.registry.ToolRegistry`:

- metadata is discovered by AST parsing;
- execution needs a hash-bound approval;
- input and output are validated against each tool's schema.

They reuse the frozen engine read-only (`detection.secrets`, `detection.script_rules`, `detection.common.noisy_or`, `detection.archives.inspect_browser_extension`, `detection.url_intel.registrable_domain`) and do not modify it.

## 1. Architecture

```
Tools/
  <category>/<tool>.py          one tool per file: literal metadata + run(input_data, options=None)
  security_toolkit/             shared helpers for 051-100 only (not an approved directory -> never discovered as a tool)
    core.py        unified result contract, run_tool() wrapper, time budget, input decoding, redaction
    textscan.py    rule engine (line/statement-scoped), Python AST helpers
    commands.py    command-line risk (LOLBins via detection.script_rules, encoded PowerShell, paths, masquerading)
    secrets_kit.py detection.secrets + 18 extra formats; masked previews and fingerprints only
    pii.py         validated personal-data detectors (Luhn, IBAN mod-97, SSN/NINO rules, Saudi ID + context)
    metadata.py    image / OOXML / PDF metadata inventories
    manifests.py   12 dependency formats, purl, OSV version ranges
    cloudrules.py  network exposure, public resource policies, IAM escalation sets, trust policies
    configparse.py .reg, key=value, safe YAML (CloudFormation tags), non-evaluating HCL reader
    dnsutil.py / httputil.py / netflow.py / winlocal.py / datasets.py
  maintenance/pin_toolkit.py    writes TOOLKIT_SHA256 and the OUTPUT_SCHEMA literal into every tool
  maintenance/build_manifest.py writes the manifest and category READMEs
  tests/tools_051_100/          276 tests
```

**Helper integrity.** Before importing anything, each tool hashes `security_toolkit/*.py` and compares the result with its own `TOOLKIT_SHA256` literal. On a mismatch it refuses to load (registry status `import_error`). Because the pin is part of the tool's source, approving a tool's hash also approves the helper code it runs. Any toolkit edit therefore requires `python Tools/maintenance/pin_toolkit.py` followed by re-approval. `test_tampered_toolkit_blocks_loading` checks this.

**Network calls** are made only by `dnsutil.lookup` / `fetch_rrsets`, `httputil.fetch` / `post_json` / `fetch_tls_chain`, and the TCP connect in tool 055. Tests replace these functions, so **no test contacts a third-party host**. Tool 055 is tested only against a listener on 127.0.0.1.

## 2. Unified output contract

Every tool returns `security_toolkit.core.UNIFIED_OUTPUT_SCHEMA`. Each tool file declares it as its `OUTPUT_SCHEMA` literal, so the registry validates it on every run.

```json
{"tool_id": "cyberscan.network.hsts", "status": "success", "classification": "review", "risk_score": 25,
 "summary": "1 finding(s): 1 medium.",
 "findings": [{"id": "hsts.missing", "title": "...", "severity": "medium", "assurance": "verified_condition", "weight": 25,
               "description": "...", "location": "...", "recommendation": "...", "references": []}],
 "evidence": [{"finding_id": "...", "kind": "excerpt", "detail": "(sanitized)", "location": "..."}],
 "artifacts": {}, "limitations": ["..."],
 "metadata": {"version": "1.0.0", "execution_mode": "network-passive", "execution_time_ms": 12, "toolkit_version": "1.0.0",
              "timeout_seconds": 20, "input_kind": "url"}}
```

- **status:**
  - `success`: the analysis ran completely.
  - `partial`: some checks were skipped (time budget, a failed lookup, an optional dependency).
  - `unsupported`: the format or platform isn't supported.
  - `unavailable`: a required dependency or service is missing; nothing was analysed.
  - `invalid_input`: the input passed the schema but can't be used.
  - `error`: an unexpected failure. The message never contains input data.
- **risk_score** fuses finding weights with the frozen engine's noisy-OR. Informational findings weigh 0.
- **classification:** `clean` (0, analysis complete), `review` (1-49), `suspicious` (≥ 50), or `unknown` (incomplete or not run).
- **assurance** keeps a detected risk distinct from a confirmed vulnerability:
  - `informational`: context only.
  - `heuristic`: a pattern; can be a false positive.
  - `verified_condition`: a fact read from the input, such as "MFA disabled" or "certificate expired". It is a weakness, not proof of exploitability.
  - `advisory_match`: a version is listed by an advisory; reachability is unverified.

  No tool emits "confirmed vulnerability".
- **Secrets never leave a tool.** Evidence is sanitised (credentials in URLs, key=value secrets and high-entropy tokens are masked), and secret findings carry only masked previews and fingerprints. Tests assert, with `no_secret_leak`, that the fake secrets in fixtures never appear in results.
- **Time budget.** The registry has no timeout. `run_tool` enforces a cooperative per-tool budget: `TIMEOUT_SECONDS`, or `options.timeout_seconds` if that is lower. When it runs out, the tool returns `partial` with what it found so far. This is not a hard kill (see section 6).

## 5. Known limitations

- **Static analysis can't confirm exploitability.** Findings are verified conditions or heuristics. The code scanners (081, 087-089) trace input only within one Python function, and other languages use line/statement patterns.
- **Live and online modes were tested only with injected network functions**, as the brief requires (no third-party targets): 051, 052, 057, 058, 059, 082 online, 092 probe. Their real-network paths use standard libraries but have not been exercised against the internet.
- **Local system modes:**
  - read-only and Windows-only for registry, netsh and schtasks; `netsh` text is parsed in English only;
  - smoke-tested on a single Windows 11 machine. That run found and fixed three false-positive sources: non-verbose netsh output, built-in tasks with resource-string authors, and Edge store update URLs.
- **068** inherits the frozen engine's capability-based scoring. Legitimate ad blockers and password managers legitimately hold "all sites + cookies" permissions and score high.
- **054** has no reputation data of its own. **082** has no vulnerability data of its own (by design: nothing is fabricated).
- **083 / 097** scan the current files only, not git history.
- **094** doesn't evaluate HCL expressions, variables, modules or `jsonencode`. Such values are listed in `artifacts.unresolved`, not guessed.
- **Time budgets are cooperative.** A single long regex or parse step is not interrupted, and the registry runs tools in-process with no hard timeout or memory limit.
- **Integrity check limits:**
  - The toolkit is checked at module load. A toolkit already imported in the same process (`sys.modules`) is reused, so a hostile process could swap files after the first load.
  - The frozen `detection` package is not part of the pin; it has its own freeze manifest.
- **There is no license file in the repository.** Each tool declares `LicenseRef-CyberScan-Unlicensed`; the owner should choose a license. Third-party packages used: dnspython (ISC), cryptography (Apache-2.0/BSD), certifi (MPL-2.0), Pillow (MIT-CMU), PyYAML (MIT), psutil (BSD-3), packaging (Apache-2.0/BSD).

3. **Dependencies.** These packages aren't declared in any requirements file yet. Proposed additions for whichever environment runs the tools:
   - `dnspython>=2.6`

   - `packaging>=23`
   - `certifi`
   - `PyYAML>=6`

   cryptography and Pillow are already in `Web/requirements.txt`.

4. **Call them:**

   ```python
   outcome = ToolRegistry().execute(tool_id, input_dict, {"timeout_seconds": 10})
   if outcome.status == "ok":
       result = outcome.result          # unified contract
   ```

   `outcome.status` is the registry's own state: `invalid_input` (schema), `disabled`, or `import_error` (for example a toolkit pin mismatch).

5. **Website exposure: important.** On a server, the `source: "local"` modes (061-069, 078, the 066 path walk, 068 local, 083 / 097 `directory`) would inspect *the server*. Active probes (055 probe, 092 probe) could be pointed at third parties. A public website must expose only the data-in tools and reject these modes; a per-tool allowlist of input keys is the simplest guard. Desktop can allow local modes for the user's own machine.

6. **Hard limits.** For untrusted, web-facing use, run tools in a worker process with a wall-clock kill. `detection.service.ScanService` already shows the pattern. This needs a shared change to the registry or execution layer, so it is proposed here, not made.
